## 2 · 指标清单与 SQL

### 2.0 统一时间基准

下面所有 SQL 都是**可直接复制执行**的（先跑这一段，再跑任意一条）。生产环境请把变量换成 `?` 占位、由 Java 传入（原因见 §2.0.1）。

```sql
-- ===== 统一时间基准（MySQL 8，GMT+8）=====
SET @now      = NOW();                                             -- 当前时刻
SET @today    = CURDATE();                                         -- 今日 00:00
SET @tomorrow = CURDATE() + INTERVAL 1 DAY;                        -- 明日 00:00（用 < 不用 <=，避开 23:59:59 精度坑）
SET @d7       = DATE(CURDATE() - INTERVAL 6  DAY);                 -- 近 7 天（含今日）起点
SET @d30      = DATE(CURDATE() - INTERVAL 29 DAY);                 -- 近 30 天（含今日）起点
SET @d90      = DATE(CURDATE() - INTERVAL 89 DAY);                 -- 近 90 天起点
SET @weekMon  = DATE(CURDATE() - INTERVAL WEEKDAY(CURDATE()) DAY); -- 本周一（WEEKDAY: 0=周一）
```

#### 2.0.1 时区：为什么生产必须参数化

`CURDATE()` / `NOW()` 取的是 **MySQL 会话时区**；JDBC 的 `serverTimezone=GMT%2B8` 只影响**驱动如何解释** `datetime`，并不改数据库会话时区。如果 DB 机器是 UTC，`CURDATE()` 会比北京时间晚 8 小时，凌晨 0–8 点的数据会算到「昨天」。

**生产写法（推荐）**：Java 侧算边界，SQL 用 `?` 绑定。

```java
private static final ZoneId ZONE = ZoneId.of("Asia/Shanghai");

LocalDate today = LocalDate.now(ZONE);
LocalDateTime todayStart    = today.atStartOfDay();                // 今日 00:00
LocalDateTime tomorrowStart = today.plusDays(1).atStartOfDay();    // 明日 00:00
LocalDateTime d30           = today.minusDays(29).atStartOfDay();
LocalDateTime weekMon       = today.minusDays(today.getDayOfWeek().getValue() - 1L).atStartOfDay();
```

### 2.2 内容与目录（K01–K06、D01、H01）

#### SQL-01 · 笔记 KPI 一次扫描

```sql
-- K01 笔记总数 / K02 近 7 天新增 / K03 环比 / K06 今日新增
SELECT
    COUNT(*)                                        AS notes,
    COALESCE(SUM(n.create_time >= @d7), 0)          AS notesDelta7d,
    COALESCE(SUM(n.create_time >= @weekMon), 0)     AS notesThisWeek,
    COALESCE(SUM(n.create_time >= @today), 0)       AS notesToday,
    ROUND(
        COALESCE(SUM(n.create_time >= @d7), 0)
        / NULLIF(COUNT(*) - COALESCE(SUM(n.create_time >= @d7), 0), 0) * 100
    , 1)                                            AS notesDeltaPct
FROM note_notes n
WHERE n.del_flag = '0';
```

> `SUM(布尔表达式)` 是 MySQL 惯用法；`create_time` 为 `NULL` 时比较得 `NULL`，`SUM` 自动忽略，外层再 `COALESCE` 兜底 0。

#### SQL-02 · 目录总数与空目录

```sql
-- K04 目录总数 / K05 空目录数（不递归子目录）
SELECT
    COUNT(*)                                        AS dirs,
    SUM(CASE WHEN c.cnt IS NULL THEN 1 ELSE 0 END)  AS emptyDirs
FROM note_directory d
LEFT JOIN (
    SELECT dir_id, COUNT(*) AS cnt
    FROM note_notes
    WHERE del_flag = '0'
    GROUP BY dir_id
) c ON c.dir_id = d.id
WHERE d.del_flag = '0';
```

> 用 `LEFT JOIN` 聚合而不是 `NOT EXISTS` 相关子查询：328 个目录时两者都 < 2ms，但目录数上千后 LEFT JOIN 明显更稳。

#### SQL-03 · 目录分布 Top N + 其他目录（D01 / D02）

```sql
-- D01/D02 按直属目录分组的全量分布（<= 328 行），Java 侧取 Top N 并合并「其他目录」
SELECT
    n.dir_id                                        AS dirId,
    COALESCE(NULLIF(d.name, ''), '未归类')          AS name,
    COUNT(*)                                        AS notes,
    COALESCE(SUM(n.update_time >= @d7), 0)          AS active7d
FROM note_notes n
LEFT JOIN note_directory d
       ON d.id = n.dir_id AND d.del_flag = '0'
WHERE n.del_flag = '0'
GROUP BY n.dir_id, d.name
ORDER BY notes DESC;
```

Java 侧合并规则（必须保证守恒：`Σ dirTop[].notes == kpi.notes`）：

```java
List<DirStat> all = mapper.selectDirDistribution(d7);      // 全量，已按 notes DESC
List<DirStat> top = all.stream().limit(query.getTop()).toList();
long topSum    = top.stream().mapToLong(DirStat::getNotes).sum();
long topActive = top.stream().mapToLong(DirStat::getActive7d).sum();
if (all.size() > top.size()) {
    top = new ArrayList<>(top);
    top.add(new DirStat("其他目录", total - topSum, active7dTotal - topActive));
}
```

> 口径说明：`dir_id = 0`（DDL 默认值）表示**未归档 / 根目录**，归入「未归类」，最终并入「其他目录」。目录分布**不递归子目录**，`note_directory.pid` 不参与统计。

#### SQL-04 · 7×24 热力（H01）

```sql
-- H01 近 30 天窗口内的编辑活跃热力（只返回有数据的桶，Java 侧补零到 7×24）
SELECT
    WEEKDAY(n.update_time)   AS wd,     -- 0=周一 … 6=周日
    HOUR(n.update_time)      AS hr,     -- 0 … 23
    COUNT(*)                 AS cnt
FROM note_notes n
WHERE n.del_flag = '0'
  AND n.update_time >= @d30
  AND n.update_time <  @tomorrow
GROUP BY wd, hr
ORDER BY wd, hr;
```

Java 补零（**必须补**，否则 ECharts 热力会出现空洞）：


### 2.3 趋势（T01–T03）

#### SQL-05 · 近 N 天新增（T01）

```sql
-- T01 近 30 天每日新增笔记（递归 CTE 补零，返回正好 30 行）
WITH RECURSIVE days AS (
    SELECT DATE(@d30) AS d
    UNION ALL
    SELECT DATE(d + INTERVAL 1 DAY) FROM days WHERE d < DATE(@today)
)
SELECT
    DATE_FORMAT(days.d, '%m/%d')        AS date,
    COALESCE(t.created, 0)              AS created
FROM days
LEFT JOIN (
    SELECT DATE(create_time) AS d, COUNT(*) AS created
    FROM note_notes
    WHERE del_flag = '0'
      AND create_time >= @d30
      AND create_time <  @tomorrow
    GROUP BY DATE(create_time)
) t ON t.d = days.d
ORDER BY days.d;
```

#### SQL-06 · 近 N 天编辑动作次数（T02）

```sql
-- T02 近 30 天每日编辑动作次数（每次保存 = 1 次）
-- title='笔记' 精确命中笔记新增 / 修改，排除 title='目录' / 'Client目录'
SELECT
    DATE_FORMAT(t.d, '%m/%d')  AS date,
    t.edited
FROM (
    SELECT DATE(o.oper_time) AS d, COUNT(*) AS edited
    FROM sys_oper_log o
    WHERE o.oper_time >= @d30
      AND o.oper_time <  @tomorrow
      AND o.business_type = 2          -- BusinessType.UPDATE
      AND o.title = '笔记'
    GROUP BY DATE(o.oper_time)
) t
ORDER BY t.d;
```

> **为什么不用 `note_notes.update_time`**：`update_time` 只保留**最后一次**更新，30 天按天分组得到的并集上限就是 12,486，而 mock 的 `Σ edited = 40,635` 明显是动作次数，两者不能混用。
>
> **为什么 `sys_oper_log` 可用**：`NoteNotesController.edit`（admin）与 `ClientNotesController.edit`（客户端）**都**标了 `@Log(title = "笔记", businessType = BusinessType.UPDATE)`，两个入口的保存都会落日志。目录操作 title 是 `目录` / `Client目录`，不会污染。

### 2.6 Redis 侧指标（K11 在线、K18 缓存命中）

```java
// K11 在线人数：Sa-Token 有效会话数
// 项目已有实现范式见 SysUserOnlineController.list()
Collection<String> keys = RedisUtils.keys(CacheNames.ONLINE_TOKEN_KEY + "*");  // "online_tokens:*"
long online = keys.stream().filter(k -> {
    String token = StringUtils.substringAfterLast(k, StringUtils.COLON);
    return StpUtil.stpLogic.getTokenActiveTimeoutByToken(token) >= -1;   // 未过期
}).count();
```

| 注意点 | 说明 |
|---|---|
| 底层不是 `KEYS` | `RedisUtils.keys()` 走 `getKeysStream(KeysScanOptions.chunkSize(1000))`，即 **SCAN 游标**，不会阻塞 Redis（`RedisUtils.java:573`） |
| 但仍是 O(keyspace) | 会话数上万时单次 20–80ms → **必须缓存 15–60s**，不能每次首屏都算 |
| 超时保护 | 每个 token 调一次 `getTokenActiveTimeoutByToken` 都是一次 Redis 往返，会话多时要并行（`ThreadUtils.virtualSubmitAll`，与 `SysUserOnlineController` 一致） |
| 失败降级 | Redis 异常时 `online = null`，前端显示「—」，**不要显示 0** |

```java
// K18 缓存命中率：Redis INFO stats 的 keyspace_hits / (keyspace_hits + keyspace_misses) * 100
// 已落地（2026-11-07）：Redisson 4.8 没有暴露 INFO 的编程接口，沿用 CacheController 的做法，
// 通过 RedissonConnectionFactory 取一条连接执行 INFO stats，用完必须归还连接池。
private double queryCacheHit() {
    RedisConnection connection = null;
    try {
        connection = redisConnectionFactory.getConnection();
        Properties stats = connection.commands().info("stats");
        long hits = parseLong(stats.getProperty("keyspace_hits"));
        long misses = parseLong(stats.getProperty("keyspace_misses"));
        long total = hits + misses;
        return total > 0 ? round2(hits * 100.0 / total) : 0.0;
    } catch (Exception e) {
        // 命中率是锦上添花指标，读不到不能拖垮首页
        log.warn("读取 Redis keyspace 命中率失败，本次降级为 0：{}", e.getMessage());
        return 0.0;
    } finally {
        if (connection != null) {
            RedisConnectionUtils.releaseConnection(connection, redisConnectionFactory);
        }
    }
}
```

> 注意：`connection.commands().info("stats")` 返回的是 **Redisson 连接**，必须走
> `RedisConnectionUtils.releaseConnection` 归还，直接 `close()` 在连接池下会报「连接已归还」。
> 同一个 60s 的 `@Cacheable` 也让这条 INFO 每 60 秒最多执行一次。

## 3 · 接口契约

### 3.1 端点

| 项 | 值 |
|---|---|
| Method / Path | `GET /notes/dashboard/overview` |
| Controller | `note-modules/note-notes/src/main/java/xin/v5ai/notes/controller/admin/NoteDashboardController.java` |
| 权限注解 | `@SaCheckPermission("notes:dashboard:query")`（sys_menu 记录已补：menu_id `1849657043265904648`，类型 F，挂在「云笔记」下，见 `db/migration/common/V4__dashboard_permission.sql`） |
| 返回 | `R<DashboardOverviewVo>` |
| 缓存 | `@Cacheable(cacheNames = CacheNames.NOTES_DASHBOARD, ...)`，TTL 60s |
| 建议耗时 | 缓存命中 < 20ms；冷启动 P95 < 200ms；前端软超时 3s |

**为什么是聚合接口而不是 8 个接口**：首页要在一屏内完成「规模 → 趋势 → 异常」的认知链。8 个并发请求会让首屏出现 8 次独立 loading 和 8 个骨架，且每个都要过一次鉴权。一个聚合接口 + 60s 缓存，把首屏压到 1 次往返。

### 3.6 缓存策略

| 层 | 键 | TTL | 说明 |
|---|---|---|---|
| Spring Cache（Redisson，项目已 `@EnableCaching`） | `notes:dashboard#60s` | 60s | 必须放在 **Service 实现类**方法上才生效（AOP 代理；同类内部调用不走缓存） |
| 在线人数 | 同上（在 `buildKpi()` 内） | 60s | 会话数扫描比其它指标贵，跟着一起缓存 |
| 前端 | `sessionStorage` | 60s | 路由来回切换不闪骨架；超时降级时用这份快照 |
| 手动刷新 | `?refresh=1` | — | 前端「刷新」按钮带 `refresh=1`，`@CacheEvict` 后重算（**待确认 #12**） |

**空结果也要缓存**：0 数据时返回结构完整的空对象（不是 `null`），否则空库会被每次请求穿透到 DB。

**击穿保护**：60s 过期瞬间若并发 10 个请求，会同时重算。项目已有 `@Lock4j`（见 `SysLoginInfoController.clean()`），可加 `@Lock4j(keys = "'dashboard:overview'", expire = 3000)` 防击穿。

### 4.1 成本评估（按设计稿数据量）

| 查询 | 扫描行数 | 有索引后预估 | 无索引预估 | 风险 |

| SQL-02 目录 / 空目录 | 328 + 12,486 | 5–10ms | 10–20ms | 低 |
| SQL-03 目录分布 | 12,486 | 10–20ms | 20–35ms | 中（GROUP BY 临时表） |
| SQL-04 热力 | 12,486（30 天窗口约 8.7k） | **20–40ms** | 30–60ms | **高**（函数分组用不上索引） |
| SQL-05 / 06 趋势 | 1.7k / 2k | 5–10ms | 20–30ms | 中 |
| SQL-09 今日登录 | ~312 | 2–5ms | 2–5ms | 低 |
| SQL-10 设备构成 | ~2.2k | 3–8ms | 5–10ms | 低 |
| SQL-12 / 13 文件 | 3,612 | 3–8ms | 5–10ms | 低 |
| SQL-14 P95 | 今日 ~2.4k + 排序 | 15–30ms | 15–30ms | 中（窗口函数排序） |
| SQL-16 最近笔记 | 6 行 + 6 次 mediumtext 读 | 10–30ms | 10–30ms | 中（大文本 IO） |

> 增长推算（按 mock 日增 86 篇）：12 个月后 `note_notes` ≈ 4.4 万，热力查询仍在 100ms 内；`sys_oper_log` 按日 2,400 条 → 年 87 万条，P95 与 24h 分组会开始吃紧。**日志表才是第一个出问题的**。

### 4.2 三个明确的慢点

| # | 慢点 | 原因 | 对策 |
|---|---|---|---|
| 1 | 热力 `GROUP BY WEEKDAY(), HOUR()` | 函数作用在列上，B+Tree 索引完全失效，必然全扫 + 临时表 | 覆盖索引（§4.3）→ 数据量破 20 万上预聚合表（§4.4） |
| 2 | `sys_oper_log` / `sys_login_info` 无上限增长 | 日志表没有归档策略，日增数千条，2 年后百万级 | 索引 `(oper_time, ...)` 覆盖 + 定时归档（`sys_oper_log` 建议保留 90 天） |
| 3 | 最近笔记读 `mediumtext` | 6 篇笔记正文可能几百 KB，走行溢出页 IO | 派生表先 `LIMIT` 再回表（SQL-16 已这样做）；或加冗余 `char_count` 列 |

### 4.3 索引建议（可直接执行）

**结论：现有 `idx_note_notes_update_time` 不够。** 三个原因：① 不带 `del_flag`，范围扫完还要回表过滤；② 完全没有 `create_time` 索引，「近 30 天新增」只能全表扫；③ 热力按函数分组，任何普通索引都用不上。

```sql
-- ===== note_notes：把 del_flag 放进聚合索引的最左列 =====

-- 1) 趋势图「每日新增」：create_time 范围扫
ALTER TABLE note_notes
    ADD INDEX idx_note_notes_del_create (del_flag, create_time);

-- 2) 趋势图「每日编辑」/ 热力 / 7 日活跃：update_time 范围扫
--    现有 idx_note_notes_update_time 只含 update_time，无法覆盖 del_flag 过滤
ALTER TABLE note_notes
    ADD INDEX idx_note_notes_del_update (del_flag, update_time);

-- 3) 目录分布 GROUP BY dir_id
ALTER TABLE note_notes
    ADD INDEX idx_note_notes_del_dir (del_flag, dir_id);

-- 4) 热力专用：生成列 + 复合覆盖索引（MySQL 8 虚拟列可建索引）
ALTER TABLE note_notes
    ADD COLUMN update_wd TINYINT GENERATED ALWAYS AS (WEEKDAY(update_time)) VIRTUAL,
    ADD COLUMN update_hr TINYINT GENERATED ALWAYS AS (HOUR(update_time))    VIRTUAL,
    ADD INDEX idx_note_notes_del_upd_wh (del_flag, update_time, update_wd, update_hr);

-- ===== 日志表 =====
ALTER TABLE sys_login_info
    ADD INDEX idx_sys_login_info_time_client (login_time, status, client_key);

ALTER TABLE sys_oper_log
    ADD INDEX idx_sys_oper_log_time_type (oper_time, business_type, title);

-- ===== 文件表 =====
ALTER TABLE basics_file
    ADD INDEX idx_basics_file_del_type (del_flag, type);
```

| 索引 | 服务的查询 | 预估收益 |
|---|---|---|
| `idx_note_notes_del_create` | SQL-01 / 05（今日新增、趋势 created） | 全表扫 → 范围扫，12k → 1.7k 行 |
| `idx_note_notes_del_update` | SQL-01 / 05 / 08（编辑趋势、7 日活跃） | 去掉回表过滤 |
| `idx_note_notes_del_dir` | SQL-03（目录分布） | 松散索引扫描，避免临时表 |
| `idx_note_notes_del_upd_wh` | SQL-04（热力） | 覆盖索引，**只读索引不读表**（避开 mediumtext 页），热力从 40ms → 10ms 量级 |
| `idx_sys_login_info_time_client` | SQL-09 / 10 | 覆盖，免回表 |
| `idx_sys_oper_log_time_type` | SQL-06 / 14 / 15 / 18 | 覆盖，免回表 |
| `idx_basics_file_del_type` | SQL-13 | 覆盖 |

> `note_notes` 带 `content mediumtext`，是宽表。**覆盖索引的价值远高于普通 OLTP 表**——它能完全不碰正文页。这是 §4.3 里最划算的一条。
>
> 写放大：新增 4 个二级索引会让每次保存多写 4 次索引页。笔记写入是低频操作（日约 1,800 次），可接受。

| 方案 | 做法 | 适用 |

### 4.5 缓存与热点

| 项 | 建议 |
|---|---|

| TTL | 60s。首页是「分钟级」语义，60s 足够；若产品要准实时看板再降到 30s |
| 冷启动 | 应用启动后第一次请求会全量算（~200ms），可选加启动预热 |

### 5.1 treemap · 目录分布

| 项 | 值 |
|---|---|
| 数据形状 | `[{ name, value, active7d }]` — **`notes` 必须映射成 `value`**（treemap 只认 `value`），`active7d` 挂在 item 上供 tooltip |
| 层数 | **单层**（不传 `children`）。目录树有 `pid`，但嵌套 treemap 在 200px 高度里会碎成不可读的碎块 |

### 5.4 面积图 · 30 天新增 vs 编辑

**先说数据问题**：`created` 峰值约 86、`edited` 峰值约 1,939，**量级差 22 倍**。同一 y 轴上 `created` 会贴成一条平线，完全看不出斜率——而 spec 要的正是「看得到斜率」，同时 spec 又明令禁止双 Y 轴。

**推荐解法：上下双 grid 共享 xAxis**（不是双 Y 轴，而是两张图叠在一个组件里，视觉上仍是一条时间轴）：

| grid[0] | `{ left:44, right:12, top:8, height:96 }` — 编辑次数，面积图 |
| grid[1] | `{ left:44, right:12, top:126, height:44 }` — 新增，迷你柱 |
| xAxis | 两个 `category`，`gridIndex:0/1`；grid[0] 的 `axisLabel.show:false`（共用下方刻度） |
| 联动 | `axisPointer: { link: [{ xAxisIndex: 'all' }] }` — 鼠标移动时两条时间轴同步高亮 |
| 面积 | **纯色低透明度** `rgba(28,90,72,.12)`，线 `#1c5a48`、`width:1.5`。**不要 LinearGradient**（spec：「无渐变堆叠」） |
| 今日未完整 | `partial:true` 的最后一点用 `markArea` 打浅色底 + 虚线，或 `itemStyle.opacity:.45` |
| 网格线 | 只留水平 `splitLine`，`lineStyle:{ color:'#e6ebe7', type:[4,4] }`；竖直网格线全关 |
| 补零 | `series` 长度必须等于 `xAxis.data.length`；缺数据用 `null`（断线）而不是 `0`（假的暴跌） |
| 兜底 | 全 0 时 `yAxis.max` 设 1，否则坐标轴塌陷 |

## 6 · 降级策略

**总原则：首页任何一块失败都不能变成白屏。** 首页是登录后的第一屏，白屏 = 用户认为系统挂了。

### 6.1 前端降级矩阵

| # | 场景 | 判定条件 | 该区块表现 | 实现要点 |
|---|---|---|---|---|
| 1 | 首屏请求中 | `loading === true` | 骨架屏：KPI 6 条灰条 + 图表区灰色占位 | **每个容器写死高度**（趋势 180 / 热力 200 / 目录 200 / 环形 140），避免 CLS 抖动 |
| 2 | 接口 200 但 `data === null` | — | 整页空状态卡：「还没有统计数据」+ 刷新按钮 | 不要渲染空 ECharts（会报 `Cannot read properties of undefined`） |
| 3 | 某区块空数组 | `arr.length === 0` | 该区块显示「暂无数据」，其余正常 | **区块级判空**，绝不整页兜底 |
| 4 | 403 无权限 | `code === 403` | 该区块显示「无权限查看该指标」+ 申请权限入口 | 只有**页面级** 403 才跳登录页 |
| 5 | 401 未登录 | `code === 401` | 跳登录（`src/utils/request.ts` 已实现，不用改） | 保留现有逻辑 |
| 6 | 超时 | 3s 软超时 | 用 `sessionStorage` 快照渲染 + 顶部条「数据更新于 10:24」 | 请求单独设 `timeout: 3000`，不要用全局 50s |
| 7 | 500 / 网络错误 | `code === 500` 或 rejected | 整页错误态 + 「重试」按钮，**保留外壳**（侧栏顶栏不消失） | 错误态也要占满主区高度 |
| 8 | 部分区块降级 | `data.meta.degraded` 含该 key | 该区块显示「该指标暂不可用」，其余正常 | 后端分区 try-catch，见 §6.2 |
| 9 | `online === null` | 值为 `null` | 显示「—」+ hover「会话服务暂不可用」 | **绝不显示 0**（0 在线是灾难信号，误报更糟） |
| 10 | 热力全 0 | `flatMax === 0` | `visualMap.max = 1` + 「窗口内无编辑」提示 | 否则 ECharts `min == max` 全白 |
| 11 | 分母为 0 | 值为 `null` | 显示「—」 | SQL 已用 `NULLIF` 兜住；前端判 `null`，不要判 `0` |
| 12 | ECharts 未加载 | `typeof window.echarts === 'undefined'` | 图表降级为「数字 + 简单进度条」列表 | 仅防御性代码，正常不会触发 |

### 6.2 后端分区容错

```java
private void safe(String key, Runnable action, List<String> degraded) {
    try {
        action.run();
    } catch (Exception e) {
        log.warn("[dashboard] 区块 {} 计算失败，已降级", key, e);
        degraded.add(key);
        // 不抛：整体仍返回 200，前端按 degraded 显示「暂不可用」
    }
}
```

| 区块 | 失败后果 | 兜底值 |
|---|---|---|
| `kpi` | 顶部 6 个数字全空 | `null`（前端骨架 →「—」） |
| `trend` / `heat` / `dirTop` | 单图空白 | 空数组 / 全 0 矩阵 |
| `online` | 一个数字 | `null` |
| `events` | 事件流空白 | 空数组 |

> 关键：**不要让一个区块的异常冒泡成 500**。分区 try-catch 让「热力图挂了但 KPI 还能看」成为可能。

### 6.3 空数据边界（新装环境 / 演示库）

| 指标 | 0 数据时的坑 | 处理 |
|---|---|---|
| `notesDeltaPct` | 除以 0 → `Infinity` / `NaN` | `NULLIF(..., 0)` → `null` → 前端「—」 |
| `avgFileMB` | 0 文件时除以 0 | 同上 |
| `successRate` | 0 条日志时除以 0 | 同上 |
| `heat` | 全 0 矩阵 | `visualMap.max = 1` |
| `dirTop` | 空数组 | 不 init treemap，显示空状态 |
| `device` | 空数组 | 不画环形 |
| `userGrowth` | 用户被清空 → 全 0 | y 轴 `max` 兜底 1 |
| `recentNotes` | `dir_id` 指向已删目录 | `LEFT JOIN` + `COALESCE('未归类')`，不会出现 `null` 目录名 |
